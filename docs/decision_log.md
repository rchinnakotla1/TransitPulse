# Decision Log

Every non-trivial choice made while building the project, with the reason. (Chronological; phase in brackets.)

| # | Phase | Decision | Reason |
|---|---|---|---|
| 1 | P0 | MBTA bus arrival/departure data, 2025 (2024 for drift) | open, per-stop scheduled vs actual times, large, documented; one city / one mode / one year as the proposal requires |
| 2 | P0 | Delayed = arrival > 5 min after schedule (timepoints only) | MBTA's own reliability standard; timepoints are where schedule adherence is defined |
| 3 | P2 | Time-based split (Jan–Aug / Sep–Oct / Nov–Dec) | agencies predict the future from the past; a random split leaks same-day conditions |
| 4 | P2 | `month` excluded as a feature | trees cannot extrapolate months never seen in training |
| 5 | P2 | Two prediction modes (planning, operational) | two different agency users with different information at prediction time |
| 6 | P2 | Daylight features added | user concern about DST / seasonal shift; test begins right after the clock change |
| 7 | P3 | LR not class-weighted; threshold tuned on validation | keeps probabilities calibrated for the dashboard |
| 8 | P3 | Final model refit on Jan–Oct | more recent data; learning curve shows recency matters more than volume |
| 9 | P3 | XGBoost Optuna on 1 M sample (was 2 M) | 2 M trials did not finish in > 1 h; tuning sample size does not change the ranking of configurations; final fit uses all rows |
| 10 | P3 | Event features kept despite negative episodic result | removing them because of test-set results would be test-set selection; logged as negative result + improvement idea |
| 11 | P3 | Retraining policy: monthly + after each schedule change | walk-forward: September (new schedule) is the only weak month; 12-month window hurts |
| 12 | P3+ | LightGBM added as 6th model with a small grid | a cross-check that the boosting result is not library-specific; not a second tuning race |
| 13 | P3+ | XGBoost stays the deployed model; LightGBM = fast retraining fallback | LGB is inside XGB's CI in both modes (0.751 vs 0.755; 0.977 vs 0.978) but 10× faster; switching would need re-tuning and re-explaining for no measurable gain |
| 14 | P4 | SHAP via XGBoost's native TreeSHAP on a 50 k stratified test sample | exact Shapley values, handles native categoricals; 50 k gives stable global ranks at a fraction of the cost; additivity asserted |
| 15 | P4 | Global surrogate = depth-4 regression tree on XGB probabilities, readable features only, fitted on validation, fidelity on test | planners asked for if-then rules; fitting on a different split than the fidelity check avoids flattering the surrogate |
| 16 | P4 | What-ifs only on planner-controllable inputs (running time, headway) + weather / live-delay scenarios; labelled "model-based, not causal" | changing e.g. a stop's history is meaningless to a user; observational data cannot support causal claims |
| 17 | P4 | LLM writes from a fact sheet only; automatic faithfulness check (no new numbers, top factor named); template fallback | prevents hallucinated causes; the app keeps working when the key expires or runs out of quota |
| 18 | P4 | No LLM-as-judge; automatic checks + a human rating rubric | an LLM grading its own family's output is circular; the automatic check is objective, the rubric lets a human rate clarity |
| 19 | P5 | Extension models: fit on 2 M train sample, early-stop on validation, test once; reuse P3 Optuna parameters | extensions are secondary questions; the simpler protocol is still fully out-of-time and avoids another ~3 h of tuning |
| 20 | P5 | Bunching = headway < 25 % of scheduled, big gap = > 150 % | standard definitions in the transit literature / close to the MBTA headway standard |
| 21 | P5 | Chronic segments identified on Jan–Oct and verified on Nov–Dec | a fix-list is only useful if it persists; checking out-of-time avoids listing one-off bad weeks |
| 22 | P4 | Fact check allows the whole-number rounding of a fact value (40.4 → "40"), nothing else | the first run rejected 20 % of LLM drafts, and all 12 were honest roundings (false positives); after the fix 5 % were rejected, all genuine (the LLM swapped the main factor) |
| 23 | P4 | Report explanation stability at feature-GROUP level as well as feature level | operational XGB vs LGB: feature ρ 0.55 because correlated live-delay features swap credit, but group ρ 0.88; explanations are communicated by group, which is the robust unit |
| 24 | P7 | Live mode scores only each bus's NEXT timepoint | the operational model was trained one-step-ahead (delay at previous timepoint -> this timepoint); scoring further timepoints would be extrapolation, so those show MBTA's own prediction |
| 25 | P7 | Bus-ahead gap measured at the first stop both trips still have a prediction for | training measures the gap at the same stop, but live the leader has usually already passed our next stop; the first common upcoming stop is the closest measurable equivalent |
| 26 | P7 | Live: skip trips not yet started and unscheduled added (-OL) trips; do not clip min_since_prev_tp at 0 | first live test scored parked buses at the terminal 15-58 min ahead (values never seen in training) and lost the behind-schedule signal (27 % of test rows have negative slack, late rate 57-100 %); after the fix only in-service buses are scored and the status line reports how many were skipped |
| 27 | P6 | Dashboard reads small pre-computed tables (`python -m src.app_data`), never the 9.8 M-row files | start-up in seconds and < 1 GB RAM; makes the site deployable on a free tier; largest table is 381 k December events |
| 28 | P6 | Show raw XGBoost probabilities, no recalibration; users pick a preset threshold | calibration already within 1 pp on the test months (26.1 % vs 25.1 %); probabilities let each user group choose its own operating point |
| 29 | P5 | Severity shown only for the operational mode (live page); keep the 1,000-tree cap | planning 4-class model finds only 10 % of major delays (misleading for riders); operational finds 80 % at 93 % precision and beats persistence; the operational run hit the cap but its >5-min AUC (0.976) already matches the binary model |
| 30 | P5/P7 | `prev_bus_gap_ratio` means "time since the last bus that has ALREADY passed the target stop" (a leader still en route is skipped). Bunching baseline scores +ratio, not -ratio; live mode rebuilds the same definition instead of using the gap to the direct leader | the first bunching baseline scored -ratio and got AUC 0.305 (< 0.5); diagnosis on 1.6 M test rows found a U-shape: ratio <= 0.25 -> 10.3 % bunched, 0.25-1 -> 2.4-2.8 %, > 2 -> 35-36 % bunched with median headway ratio 0.47, i.e. the direct leader had not passed yet and the feature describes the bus two ahead. +ratio gives AUC 0.695 / PR-AUC 0.228; XGB learns the U-shape (0.915 / 0.444). The live code measured the direct-leader gap, which is a train/serve skew exactly for bunched pairs (route 66 test: direct gap 2.45 min vs training-definition ratio 1.19); fixed in `passed_bus_features` + unit test |
| 31 | P5 | Report conformal-calibrated (CQR) 80 % delay intervals next to the raw quantile intervals; flag routes 15 and 57 (planning) as under-covered | raw intervals under-covered (75.5 % planning, 78.3 % operational). CQR margin from Sep-Oct validation: +0.33 min planning, +0.03 min operational -> test coverage 78.9 % / 79.6 % for +0.65 / +0.07 min median width. The remaining gap is the season shift (autumn calibration, winter test), which the exchangeability guarantee does not cover; planning routes 15 (70.6 %) and 57 (72.5 %) stay well below 80 %. Cheap, honest, no refit |
